# NetDiag – Network Diagnostic Web Application

**Course:** Cyber Security (IT-30001) – Web Server Security  
**Topic:** OS Command Injection  
**Variant:** Blind OS Command Injection – Time-Based  
**Platform:** Windows  
**Stack:** Node.js, Express.js, HTML, CSS and JavaScript

> **Safety notice:** This is a local classroom demonstration. The server binds to `127.0.0.1`, not a network interface. The vulnerable endpoint is deliberately constrained to the baseline value `127.0.0.1` and one fixed, harmless Windows delay payload. Do not remove these restrictions or expose this teaching application to a network.

## Problem statement

Applications sometimes pass user-controlled data into operating-system commands. If the data is concatenated into a command string and interpreted by a shell, shell metacharacters may alter the command's meaning. This weakness is commonly classified as OS command injection (CWE-78).

NetDiag demonstrates a network diagnostic feature using Windows `ping`. It provides an intentionally vulnerable teaching route and a secured route so their behavior can be compared.

## Objectives

- Build a local Node.js and Express web application.
- Accept a hostname or IPv4 address from a browser.
- Demonstrate shell interpretation in a constrained vulnerable route.
- Demonstrate a harmless time-based blind behavior without returning command output.
- Mitigate the issue with server-side validation and `execFile()` using separate arguments and `shell: false`.

## Technologies

- Node.js – JavaScript runtime.
- Express – web framework for routes and middleware.
- `child_process.exec()` – shell-based command execution used only in the constrained vulnerable demo.
- `child_process.execFile()` – direct executable invocation with separate arguments.
- HTML, CSS and browser JavaScript – user interface.

## Architecture

1. The browser loads static files from `public/`.
2. Browser JavaScript sends JSON POST requests to Express.
3. Express routes the request to `routes/diagnostic.js`.
4. The route executes Windows `ping` and measures elapsed time.
5. The backend returns a generic JSON status and elapsed time.
6. The browser updates the result panel.

## Vulnerability explanation

The vulnerable route constructs a command string:

```js
const command = `ping -n 1 ${trimmedHost}`;
exec(command, options, callback);
```

`exec()` invokes a command shell. A shell interprets metacharacters such as `&` as command separators. Therefore, a value containing shell syntax can change the command sequence.

This project intentionally permits only:
- Baseline: `127.0.0.1`
- Controlled delay payload: `127.0.0.1 & ping -n 5 127.0.0.1 > nul`

The fixed payload causes a second local ping sequence. On Windows, `ping -n 5` sends five echo requests; the interval between requests typically makes the additional command take roughly four seconds. `> nul` redirects that second command's output away from the console stream.

The endpoint does not return stdout, stderr, or the command string to the browser. It returns only a generic status and elapsed time. The additional delay is therefore a time-based side channel.

**Important limitation:** The exact-payload restriction is a safety guard for a classroom demo. It intentionally limits the vulnerable surface; it is not a general-purpose vulnerable command runner.

## Time-based blind confirmation

Run multiple trials because network scheduling, CPU load, and process startup introduce timing variation.

Expected qualitative observations (not measured results):

| Test | Input | Expected behavior |
|---|---|---|
| Vulnerable baseline | `127.0.0.1` | Short ping execution |
| Vulnerable control | `127.0.0.1` again | Similar short execution, with normal timing variation |
| Vulnerable delay | Use the displayed controlled payload | Noticeably longer, typically around four extra seconds |
| Secured baseline | `127.0.0.1` | Short ping execution |
| Secured delay input | Use the same controlled payload | Rejected by validation; no ping process is started |

The delay suggests that the shell interpreted the separator and ran the additional command. It does not reveal the command output. Repeat baseline/control and delay tests several times and compare medians rather than relying on one measurement.

## Implemented mitigation

The secured route uses:

```js
execFile("ping", ["-n", "1", trimmedHost], {
    timeout: 6000,
    windowsHide: true,
    shell: false
}, callback);
```

The host is first checked server-side. `execFile()` receives the executable separately from its argument array and does not invoke a shell when `shell: false` is used. Shell metacharacters are not parsed as command separators.

Additional defensive measures:
- Prefer a native networking library/API instead of starting an OS process.
- Validate against a strict allow-list appropriate to the application's requirements.
- Run the service with least privilege.
- Return generic errors; keep detailed diagnostics in protected server logs.
- Do not rely on character blacklists: shell syntax is complex and can be represented in many ways.
- Avoid explicitly invoking `cmd.exe /c`, PowerShell, `sh -c`, or `bash -c` with untrusted input; doing so reintroduces shell interpretation.

## Installation and testing (Windows PowerShell)

1. Install Node.js LTS from https://nodejs.org/ if it is not already installed.
2. Open PowerShell in the `NetDiag` project folder.
3. Install dependencies:

```powershell
npm install
```

4. Start the server:

```powershell
npm start
```

5. Open the application:

`http://127.0.0.1:3000`

6. Verify the backend:

`http://127.0.0.1:3000/api/health`

Expected health response:

```json
{
  "success": true,
  "message": "NetDiag server is running"
}
```

### Browser demonstration

1. Leave `127.0.0.1` in the input and select **RUN VULNERABLE**. Record the response time.
2. Repeat the same baseline request as a control.
3. Select **LOAD TEST INPUT**, then select **RUN VULNERABLE**. Observe the longer response time.
4. Keep the same payload and select **RUN SECURED**. The input should be rejected and no ping process should start.
5. Restore `127.0.0.1` and select **RUN SECURED**. It should execute a normal ping.

The only intended test target is the local loopback address. Do not test public or third-party systems.

### Direct API examples (PowerShell)

Baseline vulnerable request:

```powershell
Invoke-RestMethod -Method Post `
  -Uri http://127.0.0.1:3000/api/diagnostic/vulnerable `
  -ContentType "application/json" `
  -Body '{"host":"127.0.0.1"}'
```

Secured baseline request:

```powershell
Invoke-RestMethod -Method Post `
  -Uri http://127.0.0.1:3000/api/diagnostic/secured `
  -ContentType "application/json" `
  -Body '{"host":"127.0.0.1"}'
```

Controlled vulnerable demonstration:

```powershell
$body = @{ host = '127.0.0.1 & ping -n 5 127.0.0.1 > nul' } | ConvertTo-Json
Invoke-RestMethod -Method Post `
  -Uri http://127.0.0.1:3000/api/diagnostic/vulnerable `
  -ContentType "application/json" -Body $body
```

The same `$body` sent to `/api/diagnostic/secured` should return HTTP 400 with an input-rejected message.

## Limitations

- The application is a teaching demonstration, not a production network monitoring product.
- The vulnerable route permits only one fixed delay payload and one baseline input.
- Timing varies with system load and Windows scheduling.
- A ping response is not proof that every service on a host is available.
- The secured route validates hostname syntax but does not guarantee that a hostname resolves or that the host will reply.
- The app is bound to loopback and intended for local use only.

## Troubleshooting

- **`node` or `npm` not recognized:** Reinstall Node.js and reopen PowerShell.
- **`Cannot find module 'express'`:** Run `npm install` in the project folder.
- **Port 3000 already in use:** Stop the other server process or change `PORT` in `server.js`.
- **Cannot reach localhost:** Confirm the server is running and visit `http://127.0.0.1:3000`.
- **Ping failure:** Check Windows command availability and try `ping -n 1 127.0.0.1` in PowerShell.
- **Request timeout:** Wait for the request to finish; the server has a process timeout.

## Conclusion

NetDiag contrasts unsafe shell-based command construction with validated argument-based process execution. The controlled time-delay demonstration illustrates how blind command execution can be inferred from response timing even when command output is not returned. The secured implementation reduces this risk by validating input and avoiding shell interpretation.
